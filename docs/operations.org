#+title: Kodo Server Operations
#+subtitle: Runtime and deployment requirements for the control plane
#+startup: showall
#+options: toc:2

* Clustered deployment boundary

Kodo supports multiple Phoenix replicas connected as one distributed Erlang
cluster and backed by one PostgreSQL database. PostgreSQL session ownership
epochs are authoritative: every state transition and external effect carries
the current epoch. BEAM process discovery and node monitors provide routing and
fast failure hints, but never replace the database fence.

All replicas must be mutually reachable over Erlang distribution, use the same
cookie, use the same database, and advertise compatible session protocol
capabilities. A replica that cannot maintain its database heartbeat or
ownership authority fails closed.

* Required production identity

Every production server boot must receive both of these environment variables:

| Variable                     | Meaning                                      |
|------------------------------+----------------------------------------------|
| ~KODO_ARTIFACT_REVISION~     | Immutable identity of the deployed artifact |
| ~KODO_DEPLOYMENT_GENERATION~ | Ordered identity of the deployment rollout  |

For example:

#+begin_src sh
export KODO_ARTIFACT_REVISION="$(git rev-parse HEAD)"
export KODO_DEPLOYMENT_GENERATION="42"
export PHX_SERVER=true
bin/kodo start
#+end_src

The release pipeline or deployment system should supply these values. Do not
derive them independently inside each running replica.

** Artifact revision

~KODO_ARTIFACT_REVISION~ must be a non-empty string that identifies the exact
immutable code artifact. A Git commit SHA is suitable when one commit maps to
one artifact. An image digest or immutable build identifier is preferable when
the build can vary for the same commit.

Artifact revisions are identities, not ordered versions. Kodo must not infer
which of two artifacts is newer by comparing revision strings.

** Deployment generation

~KODO_DEPLOYMENT_GENERATION~ must contain a base-10, non-negative integer with
no suffix or surrounding content. The deployment system must increase it when
the desired rollout changes.

All replicas in one rollout receive the same generation and artifact revision.
A later rollout receives a higher generation. In particular, a rollback uses
the older artifact revision with a new, higher generation:

| Rollout          | Artifact revision | Deployment generation |
|------------------+-------------------+-----------------------|
| Initial release  | ~sha-new~         |                    41 |
| Forward rollout  | ~sha-newer~       |                    42 |
| Emergency revert | ~sha-new~         |                    43 |

This separation lets placement prefer the currently intended deployment even
when that deployment intentionally returns to older code. A CI run number,
release sequence, or another durable monotonic counter is suitable. A Git SHA,
pod restart count, timestamp generated independently by each replica, or
Kubernetes pod ordinal is not suitable.

Do not reuse a generation for different desired artifacts. Keep the counter in
a system that survives cluster replacement and rollback, such as the release
pipeline or deployment metadata store.

** Missing or invalid values

Production startup fails closed if either value is missing or invalid:

- a missing or empty ~KODO_ARTIFACT_REVISION~ raises
  ~KODO_ARTIFACT_REVISION must be a non-empty string~;
- a missing, negative, or malformed ~KODO_DEPLOYMENT_GENERATION~ raises
  ~KODO_DEPLOYMENT_GENERATION must be a non-negative integer~.

The failure occurs while ~config/runtime.exs~ is evaluated, before the Kodo
supervision tree, HTTP endpoint, or control-plane instance registration starts.
The process exits and should remain unready; the deployment system should not
restart it with invented fallback values. Correct the release configuration
and start it again.

Development defaults to artifact revision ~development~ and generation ~0~
when neither variable is supplied. If either variable is supplied in a
non-production environment, both are validated and required. Tests disable the
instance manager because application-owned heartbeat writes would sit outside
ExUnit SQL Sandbox transactions.

* Control-plane instance lifecycle

One running BEAM VM registers one durable control-plane instance record. Its
boot ID identifies that VM incarnation and is different after a new application
boot, even when the host or distributed Erlang node name is reused.

The instance manager:

1. registers the boot identity and deployment metadata in PostgreSQL;
2. marks the instance ready for future session placement;
3. refreshes its heartbeat using PostgreSQL's UTC clock;
4. marks the instance non-ready and draining during graceful application
   shutdown;
5. asks each local active session to yield at a durable model, approval, or tool
   request boundary and activates a compatible replacement before stopping the
   source coordinator. Current replicas also reconcile draining owners that
   predate the rehoming protocol, which makes its first mixed-revision rollout
   proactive without relying on old code to initiate the transfer.

Readiness in this record means eligible for session ownership. It does not
replace the HTTP or Kubernetes readiness probe. A crashed VM cannot mark itself
draining; future placement excludes it after its database heartbeat becomes
stale.

Instance registration and heartbeat failures are fatal to the instance manager
so supervision can fail closed rather than continue advertising state it can no
longer maintain.

* Control-plane database load

One replica holds the PostgreSQL advisory-lock lease for active-session
recovery. The lease is connection-scoped and is released automatically when the
recovery process, database connection, or replica exits. Non-leaders retry the
election every second by default; only the leader scans recovery candidates.
The candidate query uses the ~sessions_active_recovery_index~ partial index and
therefore reads ~running~ and ~awaiting_approval~ sessions rather than terminal
history.

The leader sweeps every 5 seconds by default. Set
~KODO_RECOVERY_SWEEP_INTERVAL~ to a positive number of milliseconds to change
that interval. With the default 15-second ownership staleness threshold,
5-second sweep, and 1-second election retry, a failed owner is normally
eligible and rediscovered within 20 seconds. Increasing the sweep interval adds
the same amount to the worst-case rediscovery bound. Decreasing it increases
database and placement traffic linearly; keep it below the required recovery
objective and avoid setting it below the heartbeat interval without measured
need. The elected recovery worker reserves one database-pool connection while
holding its lease, so production pool sizing must leave one connection for it.

Terminal coordinators stop normally after completion, failure, or cancellation.
A follow-up message reconstructs a coordinator from the durable event log. The
steady-state coordinator count should consequently follow active work, not
retained session history.

The following bounded-cardinality metrics are available in LiveDashboard and
to configured Telemetry reporters:

| Metric                                  | Tag ~operation~ values                                                    |
|-----------------------------------------+---------------------------------------------------------------------------|
| ~kodo.control_plane.query.count~        | ~instance_heartbeat~, ~recovery_election~, ~recovery_lease~, ~recovery_discovery~, ~ownership_fencing~, ~session_index_refresh~ |
| ~kodo.control_plane.query.total_time~   | The same fixed operation set                                              |

User, session, instance, and replica identifiers are deliberately excluded
from metric labels. Under the current query contracts, one heartbeat emits two
instrumented queries. Each replica emits one recovery-election query per
election attempt, plus one when a leader releases its lease normally. The
leader also emits one lease-health query per second and before each sweep. One
recovery sweep emits one discovery query plus work linear in active candidates,
one ownership assertion emits one fencing query, and one session-index row
refresh emits two queries (the scoped session and its runner). Index-invisible
durable events and events owned by unrelated users emit no session-index
refresh query.

Alert on sustained changes from these ratios rather than raw cluster totals.
Investigate recovery work that grows with completed history, heartbeat work
that grows with sessions, or index refreshes without index-visible changes.
Use query duration together with count: stable counts with rising duration
usually indicate database contention or a changed query plan, while rising
counts indicate amplification in application behavior.

* Graceful shutdown

Use an application shutdown path that invokes OTP's ~Application.prep_stop/1~.
Kodo records draining state before its supervision tree stops. Process kills,
VM crashes, and termination-grace expiry cannot perform this transition and
fall back to heartbeat-based failure detection.

Drain waits at most 20 seconds by default. A model or runner effect already in
flight is allowed to reach its next durable boundary rather than being raced by
a replacement. If no compatible target is ready or the bound expires, shutdown
continues; PostgreSQL fencing and heartbeat-based recovery remain the fallback.
Set the platform termination grace above the drain bound plus ordinary OTP
shutdown time.

* BEAM clustering

~DNS_CLUSTER_QUERY~ configures node discovery through ~DNSCluster~ in
production. It must resolve to the A or AAAA records for all Kodo replicas. Use
one fixed node basename on every replica, long names, and a unique host or pod IP:

#+begin_src sh
export RELEASE_DISTRIBUTION=name
export RELEASE_NODE="kodo@${POD_IP}"
export RELEASE_COOKIE="${KODO_ERLANG_COOKIE}"
export DNS_CLUSTER_QUERY="kodo-headless.namespace.svc.cluster.local"
#+end_src

Protect the cookie as a secret and rotate it as a coordinated cluster restart.
Do not expose Erlang distribution outside the trusted cluster network. Permit
TCP 4369 for EPMD and configure a fixed distribution port or narrow range, for
example with ~ERL_AFLAGS=-kernel inet_dist_listen_min 9100
inet_dist_listen_max 9100~, then permit that range between replicas. Network
policy, security groups, DNS, IP families, node names, and cookies must agree.

DNSCluster only initiates connections to nodes with the same basename by
default. A per-pod basename therefore prevents discovery with the current
string-valued ~DNS_CLUSTER_QUERY~ configuration.

* Placement and rollback

For sessions without a still-live owner, placement chooses ready, non-draining,
compatible instances from the highest available deployment generation, then
balances by declared capacity. Existing coordinators remain in place until
their node drains or loses authority.

The normal rollback procedure deploys the older artifact under a new, higher
generation. For an emergency move to replicas from an older generation, an
authenticated agent token may create an override:

#+begin_src sh
curl -X POST "$KODO_URL/api/cluster/placement-overrides" \
  -H "Authorization: Bearer $KODO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"artifact_revision":"sha-old","reason":"regression 1234","expires_in_seconds":600}'
#+end_src

The target artifact must be ready, compatible, and older than the highest live
generation. Overrides last from 60 to 3,600 seconds, use the PostgreSQL clock,
and fail placement closed if their target disappears. Every request is retained
with its reason, authenticated user, creation time, and expiry. The MVP has no
administrator role, so every bearer-authenticated agent user has this
cluster-wide authority; production operators must control token issuance
accordingly.

* Kubernetes without an operator

Use a headless Service for ~DNS_CLUSTER_QUERY~ and a normal Service for HTTP.
Inject these values into every Pod:

- ~POD_IP~ through the downward API for ~RELEASE_NODE~;
- one Secret-backed ~RELEASE_COOKIE~ shared by the deployment;
- immutable ~KODO_ARTIFACT_REVISION~ from the built image or release;
- one durable, monotonically increasing ~KODO_DEPLOYMENT_GENERATION~ for the
  rollout, supplied by the release pipeline rather than a pod-local counter;
- the shared ~DATABASE_URL~, ~SECRET_KEY_BASE~, and provider credentials.

Use ~RollingUpdate~ with ~maxUnavailable: 0~ and ~maxSurge~ of at least one so a
ready target exists before an old Pod terminates. The replacement must have
enough declared capacity for sessions on draining Pods. Do not use ~Recreate~
or delete all old Pods simultaneously.

An HTTP readiness probe should verify the endpoint can serve requests; initial
session placement is separately gated by Kodo's durable instance-ready flag,
which is set only after session recovery runs. A startup probe should cover
database migrations, instance registration, and initial recovery. Liveness
must allow transient database or cluster delays and should not turn a rollout
into repeated hard kills.

Set ~terminationGracePeriodSeconds~ to at least 30 seconds with the default
20-second drain bound, and increase it when provider or tool timing requires a
larger operational margin. Let Kubernetes send SIGTERM to the release so OTP
runs ~Application.prep_stop/1~; do not replace that with SIGKILL. A ~preStop~
hook is unnecessary unless the platform wrapper otherwise bypasses OTP
shutdown. A Pod that exceeds its grace may be killed, in which case ownership
heartbeats and epochs provide conservative recovery without duplicate durable
mutation.

No Kubernetes operator, custom resource, or rollout controller is required.
The release pipeline owns artifact and generation metadata; Kubernetes owns
replica replacement; Kodo owns readiness for placement, draining, handoff, and
database fencing.
